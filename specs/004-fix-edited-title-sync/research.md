# Research: 수정된 게시글 제목이 목차에 반영되지 않는 문제 수정

Technical Context에 NEEDS CLARIFICATION 항목은 없다. 아래는 설계 선택지별 결정 기록이다.

## 결정 1: 이미 목차에 있는 게시글을 신규 게시글 흐름에서 뺀다

- **Decision**: `filterCandidates` 결과에서 "처리 이력에 `deletedAt` 없이 레코드가 있고, 현재 어떤 `*_series.json`에든 URL이 들어 있는" 게시글을 제외한다(`excludeAlreadyListed`). 이 게시글들은 처리 이력의 `lastMod`가 그대로 남으므로 같은 실행의 `selectDriftCandidates`가 자연히 재확인 후보로 잡는다.
- **Rationale**: 002 spec이 이미 "이미 목차에 반영된 게시글 = 드리프트 감지 담당"으로 범위를 정의했다. 처리 주체를 하나로 정리하면 덮어쓰기 문제가 원천적으로 사라지고, 재분류(다른 시리즈로 바뀐 경우) 때 001이 새 시리즈에 append해 두 목차에 중복으로 남는 문제도 함께 막힌다. 제외된 게시글은 신규 흐름에서 조회하지 않으므로 HTTP 요청도 늘지 않는다(SC-004).
- **Alternatives considered**:
  - *001 흐름에서 처리 이력을 덮어쓰지 않기만 하기*: 이미 한 번 조회한 제목을 버리고 드리프트 단계에서 같은 게시글을 다시 조회하게 돼 요청이 2배가 된다.
  - *001 흐름에서 "이미 목차에 있음"을 감지하면 직접 제목을 갱신*: 재분류·배치 결정·재조정 로직을 001 쪽에 중복 구현하게 된다.
  - *처리 이력 레코드 존재만으로 제외*: 처리 이력에는 있지만 아직 어떤 목차에도 없는 게시글(예: 단독 시리즈 글이 나중에 기존 시리즈 이름으로 바뀜)을 001이 목차에 추가하던 기존 동작이 사라진다. 드리프트 단계는 목차에 없는 게시글을 범위 밖으로 둔다(002 Edge Cases).
  - *목차 포함 여부만으로 제외(처리 이력 조건 없음)*: 처리 이력이 없는 수동 추가 항목은 드리프트 단계가 볼 수 없어 영원히 처리 이력에 편입되지 않는다. 지금 데이터엔 그런 항목이 없지만 조건 하나로 막을 수 있다.

## 결정 2: 신규 게시글 흐름의 목차 변경을 배치 결정에도 반영한다

- **Decision**: `seriesAssignments.js`에 `addPostsToGroup(assignments, seriesFile, posts)`를 추가한다. 그룹이 없으면 `ensureGroupSeeded`로 목차 파일에서 시드하고, 각 게시글을 기존 `upsertInGroup` 규칙(공개 시각 기준 삽입, 기존 순서 불변)으로 넣는다. `index.js`는 `appendToSeries`가 성공했을 때와 `createSeriesFile`로 파일을 만들었을 때 이 헬퍼를 호출한다. 배치 결정은 실행 시작 시 한 번 읽고, 001 또는 002 단계에서 무언가 바뀌었으면 한 번 쓴다.
- **Rationale**: 재조정은 배치 결정에 있는 그룹을 목차 파일에 그대로 덮어쓰므로, 배치 결정이 목차보다 적은 항목을 가지면 그 차이만큼 지워진다(swemo 435 사례). 001이 쓰는 모든 목차 변경을 배치 결정에도 기록하면 두 저장소가 어긋나는 경로가 없어진다.
- **Alternatives considered**:
  - *재조정 직전에 목차 파일에만 있는 항목을 배치 결정에 병합*: 삭제·재분류로 의도적으로 뺀 항목과 구분할 수 없어 삭제가 되살아난다.
  - *001이 목차 파일을 직접 쓰지 않고 배치 결정만 갱신한 뒤 재조정에 맡기기*: 001의 append-only 동작과 커밋 카테고리(항목 추가/생성) 집계 경로가 바뀌어 변경 범위가 커진다.

## 결정 3: 기존 불일치 3건은 일회성으로 복구한다

- **Decision**: 처리 이력의 현재 제목을 정답으로 보고, 세 목차 항목과 배치 결정의 제목을 고치고 swemo 그룹에 435를 넣는다(공개 시각 기준 삽입 → 427 뒤). 복구 스크립트는 저장소에 남기지 않고 결과 데이터만 커밋한다.
- **Rationale**: 세 게시글은 처리 이력의 `lastMod`가 이미 sitemap과 같아 고친 코드로도 "변경 없음"이다. 상시 자가 치유 장치(매 실행마다 처리 이력과 목차 전체 대조)는 이번 3건만을 위해 남는 코드이고, 앞으로의 불일치는 원인이 제거됐으며 무결성 테스트(결정 4)로 감지된다 — 오버엔지니어링 금지 요구에 따른다.
- **Alternatives considered**: 처리 이력의 `lastMod`를 지워 다음 실행에서 재확인하게 하기 — 결정 1·2가 배포된 뒤에만 의미가 있고, 실행 시점에 결과가 달려 검증이 어렵다.

## 결정 4: 회귀 테스트 구성

- **Decision**:
  1. `run.test.js`(신규): 임시 디렉터리를 작업 디렉터리로 쓰고 전역 `fetch`를 sitemap/게시글 HTML 고정 응답으로 바꿔 `run()`을 실제로 돌린다. (a) 이미 목차에 있는 게시글의 제목이 바뀌고 lastmod가 커트라인보다 새로울 때 목차 제목이 갱신되는지, (b) 신규 흐름으로 추가된 항목이 다음 실행의 드리프트 재조정 후에도 남는지 확인한다.
  2. 단위 테스트: `excludeAlreadyListed`, `addPostsToGroup`.
  3. `seriesDataIntegrity.test.js`: 실제 저장소 데이터에서 처리 이력↔목차 제목 일치, 배치 결정↔목차 구성(URL 집합·제목) 일치.
- **Rationale**: 이번 버그는 두 흐름의 상호작용에서 생겼으므로 각 함수 단위 테스트만으로는 재현되지 않았다(기존 테스트 전부 통과 상태에서 발생). `run()` 통합 테스트가 원인을 그대로 재현하는 유일한 방법이다. 무결성 테스트는 같은 종류의 데이터 어긋남이 다른 경로로 생겨도 `npm test`에서 바로 드러나게 한다.
- **Alternatives considered**: 통합 테스트를 위해 `run()`을 의존성 주입 구조로 리팩터링 — 프로덕션 코드 변경이 커진다. `node --test`는 파일마다 별도 프로세스로 실행되므로, 테스트 파일 안에서 `process.chdir`과 `globalThis.fetch` 교체만으로 충분하다.
