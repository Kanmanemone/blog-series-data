**Status**: Draft

**Input**: User description: "이미 시리즈 목차(*_series.json)에 반영된 게시글의 제목을 티스토리에서 수정해도 목차 제목이 갱신되지 않는 버그 수정. 실측 사례: swemo_series.json의 https://kenel.tistory.com/435가 예전 제목 \"Swemo - Iteration 8: Label과 Text 분리\"로 남아 있음(현재 제목 \"Swemo - Iteration 8: Bulleted List 구현\"). 같은 원인으로 그래프_series.json의 212, 2026buildwithaihands-oncampus_series.json의 412도 불일치. 목표: 원인 수정, 기존 불일치 3건 복구, 재발 방지 회귀 테스트. 오버엔지니어링 금지."

## 원인 분석 (실측, 2026-10-10)

002-post-drift-detection은 "이미 목차에 반영된 게시글의 제목이 바뀌면 목차도 갱신한다"(002 User Story 1)를 약속했지만, 실제 운영에서는 이 경로가 거의 한 번도 작동하지 않았다.

1. 게시글을 수정하면 공개 게시글 목록의 최근 수정 시각(lastMod)이 직전 실행의 커트라인보다 새로워진다. 그래서 그 게시글은 001의 **신규 게시글 처리 흐름** 후보에 먼저 잡힌다(001은 "커트라인 이후 수정된 모든 게시글"을 후보로 삼으며, 처리 이력에 이미 있는지는 보지 않는다).
2. 신규 게시글 흐름은 그 게시글이 이미 목차에 있으므로 목차에 추가하지 않고 "정보 갱신"으로만 집계한 뒤, **처리 이력의 제목과 마지막 확인 수정 시각을 새 값으로 덮어쓴다.**
3. 같은 실행의 002 드리프트 감지 단계는 "처리 이력의 마지막 확인 수정 시각 < 현재 수정 시각"인 게시글만 재확인하는데, 2에서 두 값이 이미 같아졌으므로 변경이 없다고 판단한다. 다음 실행부터도 마찬가지다 — 제목 변경이 **영구히** 목차에 반영되지 않는다.

실측 근거: 2026-10-08 정기 실행 커밋(`94da678`)은 435의 처리 이력 제목만 새 제목으로 바꾸고 "게시글 - 정보 갱신: 1건"으로 기록했으며, `swemo_series.json`과 배치 결정(`.github/series-assignments.json`)은 변경하지 않았다. 배치 결정 파일은 2026-08-12 이후 한 번도 갱신되지 않았다. 처리 이력과 목차 파일을 전수 대조한 결과 같은 원인의 불일치는 3건이다:

| 목차 파일 | 게시글 | 목차의 (옛) 제목 | 처리 이력의 (현재) 제목 |
|---|---|---|---|
| `swemo_series.json` | /435 | Swemo - Iteration 8: Label과 Text 분리 | Swemo - Iteration 8: Bulleted List 구현 |
| `그래프_series.json` | /212 | 그래프 - 깊이 우선 탐색 (DFS, Depth-First Search) | 그래프 - 깊이 우선 탐색 (DFS, Depth-First Search), 백트래킹 (Backtracking) |
| `2026buildwithaihands-oncampus_series.json` | /412 | … (feat.Kotlin | … (feat.Kotlin) |

**잠재 위험(같이 고쳐야 함)**: 001의 신규 게시글 흐름이 목차에 항목을 추가하거나 목차 파일을 새로 만들 때 배치 결정에는 반영하지 않는다. 그래서 현재 배치 결정의 Swemo 그룹에는 435가 아예 없다. 위 1~3만 고쳐 드리프트 경로가 다시 작동하기 시작하면, 다음에 Swemo의 다른 게시글이 수정되는 순간 재조정 단계가 "배치 결정에 없는 435"를 목차에서 **지워버린다.**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 수정된 제목이 다음 정기 실행에서 목차에 반영된다 (Priority: P1)

시리즈 목차 관리자로서, 이미 목차에 반영된 게시글의 제목을 수정하면, 손대지 않아도 다음 정기 실행에서 목차의 제목이 새 제목으로 바뀌기를 원한다.

**Why this priority**: 이번 버그의 본체다. 002가 약속한 핵심 가치("목차 정확성 유지")가 실제로는 작동하지 않고 있다.

**Independent Test**: 목차에 반영된 게시글의 제목과 수정 시각만 바꾼(수정 시각이 직전 커트라인보다 새로운) 공개 목록으로 정기 실행을 한 번 돌려, 그 목차 항목의 제목이 새 제목으로 바뀌고 커밋 요약에 "시리즈 - 제목 갱신"으로 집계되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 목차에 반영된 게시글 A의 제목이 수정되어 수정 시각이 직전 커트라인보다 새로울 때, **When** 정기 실행이 돌면, **Then** 같은 실행에서 목차의 A 항목 제목이 새 제목으로 갱신되고 커밋 요약에는 "시리즈 - 제목 갱신"으로 집계된다("게시글 - 정보 갱신"으로만 집계되고 끝나지 않는다).
2. **Given** 게시글 A의 제목이 수정되면서 시리즈 구분 기준이 다른 기존 시리즈로 바뀌었을 때, **When** 정기 실행이 돌면, **Then** A는 002의 재분류 규칙대로 옛 시리즈에서 빠지고 새 시리즈에 들어간다(두 목차에 동시에 남지 않는다).
3. **Given** 목차에 반영된 게시글 A가 제목은 그대로이고 본문만 수정되었을 때, **When** 정기 실행이 돌면, **Then** 목차 파일은 바뀌지 않는다.

### User Story 2 - 신규 게시글 흐름으로 추가된 항목이 이후 재조정에서 사라지지 않는다 (Priority: P1)

시리즈 목차 관리자로서, 새 글이 기존 시리즈 목차에 자동으로 추가되거나 새 목차 파일이 생긴 뒤, 그 시리즈의 다른 글을 수정해도 앞서 추가된 항목이 목차에서 사라지지 않기를 원한다.

**Why this priority**: User Story 1을 고치는 순간 실제로 발현되는 데이터 손실 위험이다. User Story 1과 함께 배포되어야 한다.

**Independent Test**: 신규 게시글 흐름으로 기존 시리즈 목차에 게시글 N을 추가하는 실행 직후, 같은 시리즈의 다른 게시글 제목이 바뀌는 실행을 한 번 더 돌려 N이 목차에 그대로 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 신규 게시글 N이 기존 시리즈 S의 목차에 추가되었을 때, **When** 같은 실행이 끝나면, **Then** 배치 결정의 S 그룹에도 N이 들어 있다.
2. **Given** 신규 게시글 흐름이 시리즈 T의 목차 파일을 새로 만들었을 때, **When** 같은 실행이 끝나면, **Then** 배치 결정의 T 그룹이 그 목차 파일의 모든 항목을 담고 있다.
3. **Given** 위 1이 반영된 상태에서 S의 다른 게시글 제목이 바뀌었을 때, **When** 다음 정기 실행이 돌면, **Then** 그 게시글의 제목만 갱신되고 N은 목차에 그대로 남는다.

### User Story 3 - 이미 어긋난 3건이 복구된다 (Priority: P2)

시리즈 목차 관리자로서, 이 버그로 이미 어긋난 목차 항목 3건(435, 212, 412)이 현재 제목으로 바로잡히고, 배치 결정의 누락(Swemo 그룹의 435)도 채워지기를 원한다.

**Why this priority**: 원인을 고쳐도 이미 처리 이력이 새 값으로 덮어써진 3건은 "변경 없음"으로 보이므로 자동으로 복구되지 않는다. 일회성 데이터 복구가 필요하다.

**Independent Test**: 처리 이력과 모든 목차 파일, 배치 결정을 대조해 제목 불일치 0건, 목차에는 있는데 배치 결정에 없는 항목 0건인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 복구가 끝났을 때, **When** 모든 목차 항목의 제목을 처리 이력의 제목과 비교하면, **Then** 불일치가 0건이다.
2. **Given** 복구가 끝났을 때, **When** 배치 결정의 각 그룹을 같은 이름의 목차 파일과 비교하면, **Then** 게시글 구성과 제목이 일치한다.

---

### Edge Cases

- 처리 이력에는 있지만 아직 어떤 목차에도 없는 게시글이 수정되면? → 지금처럼 신규 게시글 흐름이 처리한다(제목이 기존 시리즈에 맞게 바뀌었다면 그 목차에 추가될 수 있다). 이번 수정은 "이미 목차에 있는" 게시글의 처리 주체만 바꾼다.
- 이미 목차에 있는 게시글의 재확인(제목 조회)이 이번 실행에서 실패하면? → 처리 이력을 덮어쓰지 않으므로 다음 실행에서 다시 재확인 후보가 된다(002의 기존 동작).
- 이번 실행의 커트라인 이후 후보가 전부 "이미 목차에 있는 게시글"뿐이면? → 이들은 드리프트 감지 단계가 처리하므로 누락되지 않는다. 커트라인 진행 규칙은 바꾸지 않는다.
- 삭제 확정된 뒤 다시 공개된 게시글? → 이번 범위 밖(기존 동작 유지).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 신규 게시글 처리 흐름은 처리 이력에 (삭제 확정되지 않은 상태로) 이미 있고 어떤 목차 파일에도 이미 반영된 게시글을 처리하지 않아야 한다 — 그런 게시글의 변경 감지·반영은 002의 드리프트 감지 단계가 전담한다. 그 결과 처리 이력이 드리프트 감지 전에 새 값으로 덮어써지지 않아야 한다.
- **FR-002**: 목차에 반영된 게시글의 제목이 바뀌면, 그 수정이 감지된 정기 실행에서 목차 항목 제목이 새 제목으로 갱신되어야 하며, 커밋 요약에는 "시리즈 - 제목 갱신"으로 집계되어야 한다.
- **FR-003**: 신규 게시글 처리 흐름이 기존 목차에 항목을 추가하거나 목차 파일을 새로 만들면, 같은 실행 안에서 배치 결정에도 동일한 소속과 제목이 반영되어야 한다.
- **FR-004**: 이미 어긋난 3건(435, 212, 412)의 목차 제목을 처리 이력의 현재 제목으로 복구하고, 배치 결정의 제목·누락 항목(Swemo 그룹의 435)도 맞춰야 한다. 복구는 일회성이며 상시 자가 치유 장치를 새로 만들지 않는다.
- **FR-005**: 위 1~3단계 원인을 그대로 재현하는 회귀 테스트(수정 시각이 커트라인보다 새로운, 이미 목차에 있는 게시글의 제목 변경 → 목차 갱신)와, 신규 흐름 추가 직후 재조정이 그 항목을 지우지 않는지에 대한 회귀 테스트가 있어야 한다.
- **FR-006**: 저장소 데이터 무결성 테스트는 (a) 모든 목차 항목의 제목이 처리 이력의 제목과 같고, (b) 모든 목차 파일의 게시글 구성이 배치 결정과 같은지 확인해야 한다 — 이번 같은 불일치가 다시 생기면 테스트 실행 시 바로 드러난다.

### Key Entities

- **처리 이력 (Processed Post, `.github/sync-state.json`)**: 게시글별 마지막으로 확인한 제목·수정 시각. 드리프트 감지의 기준값이므로, 실제로 목차 반영을 판단하기 전에 덮어써지면 안 된다.
- **배치 결정 (Series Assignment, `.github/series-assignments.json`)**: 시리즈별 소속 게시글과 제목. 재조정 단계가 목차 파일을 이것과 똑같이 맞추므로, 목차 파일에 들어간 모든 항목을 담고 있어야 한다.
- **시리즈 목차 (`*_series.json`)**: 공개되는 결과물.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 이미 목차에 반영된 게시글의 제목을 수정하면, 수정 이후 첫 정기 실행 1회 안에 목차 제목이 새 제목과 같아진다(현재는 무기한 불일치).
- **SC-002**: 복구 직후 처리 이력과 목차 간 제목 불일치 0건, 목차와 배치 결정 간 구성 불일치 0건.
- **SC-003**: 신규 게시글 흐름으로 목차에 추가된 항목이 이후 재조정으로 사라지는 경우 0건.
- **SC-004**: 이번 수정으로 정기 실행당 추가로 발생하는 게시글 조회 요청 0건(같은 게시글을 두 번 조회하지 않는다).

## Assumptions

- 처리 이력·배치 결정·목차 파일의 구조(스키마)는 바꾸지 않는다(Constitution I).
- 목차 항목 순서는 기존 규칙(배치 결정의 순서, 신규 항목은 공개 시각 기준 삽입)을 그대로 따른다. 복구 과정에서 기존 항목의 순서는 바꾸지 않는다.
- 412의 불일치("(feat.Kotlin" → "(feat.Kotlin)")도 처리 이력 제목이 현재 실제 제목이라고 보고 같은 방식으로 복구한다.
- 커밋 메시지 형식, 워크플로우 트리거, 커트라인 계산 규칙은 바꾸지 않는다.
- 작업 결과는 기능 브랜치에 커밋하며, 정기 실행이 도는 기본 브랜치로의 병합·push는 관리자가 직접 판단한다.
