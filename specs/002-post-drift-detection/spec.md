- Q: 게시글의 시리즈 구분 기준이 바뀌어 다른 시리즈로 재분류될 때, 기존 시리즈 파일에서 그 항목을 자동으로 제거해도 괜찮을까요? → A: 완전 자동 재분류 — 기존 목차 파일에서 즉시 제거하고 새로 식별된 시리즈의 목차 파일에 추가까지 자동으로 수행한다. 문제가 발견되면 저장소 관리자가 직접(예: git revert) 되돌린다.
- Q: 재분류로 인해 기존 시리즈 목차 파일의 항목이 1개 이하로 줄어들면, 그 파일을 어떻게 처리해야 할까요? → A: 1개 이하로 줄어들면 목차 파일을 자동으로 삭제한다(001의 2개 이상 생성 기준을 제거 시에도 대칭 적용).
- Q: 게시글 드리프트 처리 로직을 어떤 구조로 나눌까요? → A: 세 계층으로 분리한다 — (1) sitemap lastMod로 재확인 후보를 선별하고 전체 제목을 보유하는 처리 이력(001의 sync-state 확장), (2) 처리 이력의 변경분만 반영해 게시글-시리즈 소속을 부분 갱신하는 배치 결정 기록(신규), (3) 매 실행마다 배치 결정 전체와 실제 시리즈 목차 파일 전체를 비교해 다른 부분만 고치는 재조정. 기존에 개별 규칙으로 흩어져 있던 제목 갱신·재분류·고아 파일 삭제가 이 재조정 원칙 하나로 통합된다.
- Q: 게시글이 삭제·비공개 전환으로 확정되면, 배치 결정에서 완전히 제외해 목차 파일에서도 자동으로 제거할까요, 아니면 배치 결정에는 남겨두고 실제 파일은 건드리지 않은 채 플래그만 남길까요? → A: 완전히 제외한다 — 배치 결정에서 삭제 확정 게시글을 제외하고, 그 결과로 목차 파일에서도 자동으로 제거한다(실행 로그에만 기록). 재분류·고아 파일 삭제와 동일하게 무검토 자동 push 모델을 적용하며, 문제가 발견되면 관리자가 직접 되돌린다.
- Q: 실제로 반영된 변경(생성·갱신·삭제)을 어디에 기록하면 좋을까요? (앞선 "정기 실행 결과 요약(워크플로우 로그)" 결정을 재검토) → A: 워크플로우 실행 로그 대신 커밋 메시지에 남긴다. GitHub Actions 로그는 보존 기간이 지나면 사라지지만 git 커밋 히스토리는 영구적이며, 001이 이미 커밋을 유일한 변경 기록 수단으로 쓰고 있어 자연스럽다. 삭제뿐 아니라 이번 실행에서 실제로 생성·갱신·삭제한 모든 항목(제목 갱신, 재분류 이동, 목차 파일 생성·삭제, 삭제·비공개 전환으로 인한 제거)을 커밋 메시지에 요약하며, 매번 같은 고정 문구를 쓰지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 제목 변경 자동 반영 (Priority: P1)

시리즈 목차 관리자로서, 이미 시리즈 목차에 반영된 게시글의 제목을 나중에 수정하면, 수동으로 손대지 않아도 목차의 제목이 결국 실제 제목과 같아지기를 원한다.

**Why this priority**: 001-tistory-series-sync가 명시적으로 남겨둔 두 간극 중 더 근본적인 것 — 지금은 재확인 메커니즘이 전혀 없어 목차와 실제 게시글 제목이 무기한 어긋난 채로 남는다. 이 스토리 하나만 구현해도 "목차 정확성 유지"라는 핵심 가치를 전달한다.

**Independent Test**: 목차에 이미 반영된 게시글 하나의 실제 제목을 바꾼 뒤 정기 확인이 한 번 돌면, 다른 스토리 없이도 그 항목의 목차 제목이 새 제목으로 바뀌었는지만으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 목차에 반영된 게시글 A가 여전히 공개 상태이고 마지막 확인 이후 실제로 수정되었을 때, **When** 정기 확인이 실행되면, **Then** 게시글 A의 현재 제목을 다시 확인해 목차의 제목을 최신 값으로 갱신한다.
2. **Given** 게시글 A가 마지막 확인 이후 전혀 수정되지 않았을 때, **When** 정기 확인이 실행되면, **Then** 게시글 A의 제목을 다시 확인하지 않고 목차도 변경하지 않는다.
3. **Given** 게시글 A의 제목이 바뀌면서 시리즈 구분 기준(예: 구분자 앞부분)이 함께 달라졌고, 새로 식별된 시리즈가 이미 목차 파일을 갖고 있거나 이번 이동만으로 2개 이상의 게시글 요건을 충족할 때, **When** 목차가 갱신되면, **Then** 게시글 A는 기존 시리즈 목차 파일에서 제거되고(필요 시 그 파일이 삭제되고) 새로 식별된 시리즈의 목차 파일에 새 제목으로 추가된다(필요하면 새 파일을 생성한다).
4. **Given** 게시글 A가 재분류되어 기존 시리즈 목차 파일에 남는 항목이 1개 이하가 될 때, **When** 재분류가 반영되면, **Then** 그 시리즈 목차 파일은 자동으로 삭제된다.
5. **Given** 게시글 A의 제목이 바뀌면서 시리즈 구분 기준이 달라졌지만, 새로 식별된 시리즈가 아직 목차 파일이 없고 이번 이동만으로는 2개 이상의 요건을 충족하지 못할 때, **When** 목차가 갱신되면, **Then** 게시글 A는 기존 시리즈 목차 파일에 그대로 남고 다음 정기 확인에서 요건 충족 여부를 다시 판단한다(재분류 대상 게시글이 어느 목차에도 없는 상태가 되지 않도록 한다).

### User Story 2 - 삭제·비공개 전환 자동 반영 (Priority: P2)

시리즈 목차 관리자로서, 이미 목차에 반영된 게시글이 삭제되거나 비공개로 전환되면, 수동으로 손대지 않아도 목차에서 그 항목이 사라지고, 언제 어떤 게시글이 그렇게 됐는지는 실행 기록으로 확인할 수 있기를 원한다.

**Why this priority**: 방치하면 목차에 죽은 링크가 무기한 남는다는 문제는 실재한다. 이번 기능은 제목 갱신·재분류·삭제를 "배치 결정과 실제 목차 파일을 비교해 다른 부분만 고친다"는 하나의 재조정 원칙으로 통합하기로 확정했으므로(Clarifications 참고), 삭제만 별도의 예외로 남기지 않는다. User Story 1과 독립적으로 가치를 전달한다.

**Independent Test**: 목차에 반영된 게시글 하나가 더 이상 공개 목록에서 확인되지 않는 상태를 만든 뒤 정기 확인이 한 번 돌면, 다른 스토리 없이도 그 게시글이 목차에서 자동으로 사라지고 그 사실이 실행 기록에 남는지만으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 목차에 반영된 게시글 B가 이번 정기 확인에서 공개 게시글 목록 조회가 성공했음에도 그 결과에 없을 때, **When** 그 상태가 삭제·비공개 전환으로 확정되면, **Then** 게시글 B는 배치 결정에서 제외되고, 그 결과 목차에서도 자동으로 제거되며, 이 사실이 해당 정기 실행의 커밋 메시지에 반영된다.
2. **Given** 이번 정기 확인에서 공개 게시글 목록 조회 자체가 실패했을 때, **When** 정기 확인이 실행되면, **Then** 목록을 확보하지 못했으므로 이번 실행에서는 어떤 게시글도 삭제·비공개 전환으로 판단하지 않으며 목차도 변경하지 않는다(기존 목록 조회 실패 처리와 동일하게 이번 실행의 판단을 보류한다).
3. **Given** 게시글 B가 이미 삭제·비공개 전환으로 확정되어 목차에서 제거된 상태일 때, **When** 다음 정기 확인이 다시 실행되면, **Then** 이미 제거된 게시글을 다시 재확인 후보로 삼거나 중복으로 기록하지 않는다.

### Edge Cases

- 목차(시리즈 json)에는 아직 반영되지 않았지만 처리 이력에만 남아있는 게시글의 제목이 바뀌면 어떻게 되는가? → 이번 기능은 "이미 목차에 반영된" 게시글만 대상으로 하므로 범위 밖이다.
- 한 게시글이 마지막 확인 이후 수정된 것으로 보이는 동시에 공개 목록에서도 사라진 것처럼 보이는 모순적 상황이면 어떻게 되는가? → 공개 목록에서 확인되지 않으면 수정 여부 자체를 판단할 재료가 없으므로 삭제·비공개 전환 확정(배치 결정에서 제외) 처리를 우선한다.
- 공개 게시글 목록 조회 자체가 실패하면 어떻게 되는가? → 기존 001과 동일하게 이번 실행을 중단하며, 삭제·비공개 전환 판단도 제목 갱신도 수행하지 않는다(다음 정기 확인에서 다시 시도).
- 이번 기능 도입 이전에 처리된 기존 게시글은 "마지막 확인 시점" 기준값이 없는데 어떻게 처리하는가? → 기준값이 없으면 "변경 여부 불명"으로 간주해 다음 정기 확인에서 한 번은 반드시 확인 대상에 포함시킨다.
- 같은 실행 동안 다수의 게시글이 동시에 수정된 것으로 확인되면 어떻게 되는가? → 확인 대상이 늘어난 만큼만 처리하며, 대상 수가 비정상적으로 많아지는 경우의 처리 방식은 이번 스펙에서 확정하지 않는다(Assumptions 참고).
- 재분류 대상 게시글의 새 시리즈가 아직 목차 파일 생성 기준(2개 이상)을 충족하지 못하면 어떻게 되는가? → 게시글을 기존 시리즈 목차 파일에 그대로 두고 다음 정기 확인에서 다시 판단한다 — 재분류 대상 게시글이 어느 목차에도 없는 상태를 만들지 않는다.
- 재분류나 삭제·비공개 전환으로 시리즈 목차 파일의 항목이 1개 이하로 줄어들면 어떻게 되는가? → 원인과 무관하게 동일한 재조정 규칙에 따라 그 목차 파일을 자동으로 삭제한다.
- 같은 게시글이 이번 실행에서 제목 변경(재분류 포함)과 삭제·비공개 전환 판단 대상이 동시에 되면 어떻게 되는가? → 공개 목록에서 확인되지 않으면 제목·재분류 판단 자체를 하지 않고 삭제·비공개 전환 확정 처리를 우선한다.
- 삭제 확정되어 배치 결정에서 제외된 게시글의 처리 이력은 어떻게 되는가? → 처리 이력에는 "삭제 확정" 상태로 남겨, 같은 게시글이 다음 실행에서 다시 재확인 후보로 잡히지 않도록 한다.
- 배치 결정은 이번에 바뀐 게시글만 부분적으로 갱신되는데, 실제 목차 파일과의 비교·반영도 부분적으로만 이뤄지는가? → 아니다. 배치 결정 갱신 자체는 부분적이지만, 그렇게 갱신된 배치 결정 전체와 실제 목차 파일 전체를 비교하는 반영 단계는 매 실행마다 전체 범위로 수행된다 — 그래야 반영 결과가 항상 최신 배치 결정 전체와 일치한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 정기 확인 시점마다 공개 게시글 목록과 각 게시글의 최근 수정 시각(lastMod)을 조회해야 한다.
- **FR-002**: 시스템은 목차에 이미 반영된 게시글마다, 처리 이력에 저장된 마지막 확인 수정 시각과 이번에 새로 조회한 수정 시각을 비교해 다시 확인할 후보를 선별해야 한다.
- **FR-003**: 시스템은 선별된 후보에 대해서만 실제 현재 제목을 다시 조회해야 한다(선별되지 않은 게시글은 제목을 다시 조회하지 않는다).
- **FR-004**: 시스템은 다시 조회한 게시글의 전체 제목과 수정 시각을 처리 이력에 반영해야 한다(시리즈명 일부가 아니라 제목 전체를 보유한다).
- **FR-005**: 시스템은 공개 게시글 목록 조회가 성공했음에도 목차에 이미 반영된 게시글이 그 결과에 없으면, 별도의 연속 확인 절차 없이 즉시 삭제·비공개 전환으로 확정해야 한다. 공개 게시글 목록 조회 자체가 실패한 실행에서는 어떤 게시글도 삭제·비공개 전환으로 판단하지 않아야 한다.
- **FR-006**: 시스템은 게시글의 시리즈 소속을 담은 배치 결정을, 처리 이력의 제목이 이번 실행에서 새로 확인됐거나 삭제가 새로 확정된 게시글에 대해서만 갱신해야 한다 — 변경되지 않은 게시글의 배치 결정은 다시 계산하지 않는다.
- **FR-007**: 시스템은 삭제·비공개 전환이 확정된 게시글을 배치 결정에서 제외해야 한다.
- **FR-008**: 시스템은 매 실행마다 배치 결정 전체(게시글별 소속 시리즈와 제목)와 실제 시리즈 목차 파일 구조 전체를 비교해, 일치하지 않는 부분(누락된 항목, 더 이상 속하지 않는 항목, 제목이 다른 항목)만 실제 파일에 반영해야 한다 — 이미 일치하는 파일·항목은 다시 쓰지 않는다.
- **FR-009**: 시스템은 배치 결정상 더 이상 어떤 시리즈에도 속하지 않게 된 게시글의 항목을, 그 게시글이 속해 있던 시리즈 목차 파일에서 제거해야 한다.
- **FR-010**: 시스템은 배치 결정상 새로 속하게 된 게시글의 항목을 해당 시리즈의 목차 파일에 추가해야 한다. 대상 목차 파일이 아직 없을 때는, 배치 결정상 해당 시리즈에 속한 게시글이 2개 이상이면 새로 생성해야 한다(001의 기존 생성 기준과 동일).
- **FR-011**: 시스템은 배치 결정상 어떤 시리즈에 속한 게시글이 2개 미만이면, 그 시리즈의 목차 파일을 생성하지 않아야 하며(아직 없던 경우), 이미 있던 경우 삭제해야 한다.
- **FR-012**: 시스템은 이번 실행에서 실제로 반영한 변경(생성되거나 삭제된 시리즈 목차 파일, 추가·갱신·제거된 항목)을 구분해, 그 내용을 정기 실행의 커밋 메시지에 요약으로 기록해야 한다 — 변경 내용이 다른 두 실행이 동일한 고정 문구를 반복해서는 안 된다.
- **FR-013**: 시스템은 이미 삭제·비공개 전환으로 확정 처리한 게시글을 다음 정기 확인에서 다시 재확인 후보로 삼지 않아야 한다.
- **FR-014**: 이 감지·반영 동작은 001의 기존 정기 실행 안에서 이어서 수행되어야 한다(별도 워크플로우로 분리하지 않는다).

### Key Entities *(include if feature involves data)*

- **처리 이력 레코드**: 목차에 반영되었거나 반영을 시도했던 게시글 하나에 대한 변경 감지용 기록. 게시글 URL, 마지막으로 확인한 전체 제목, 마지막으로 확인한 수정 시각(lastMod), 마지막 처리 시각, 삭제·비공개 전환 확정 여부를 가진다. 001의 기존 처리 이력을 확장한 것이며, 시리즈명 일부(rawSeriesName)가 아니라 제목 전체를 보유한다.
- **배치 결정 레코드**: 게시글이 현재 어느 시리즈에 속하는지, 그 시리즈 안에서 어떤 제목으로 나타나야 하는지를 담은 신규 기록. 처리 이력에서 제목이 바뀌었거나 삭제가 새로 확정된 게시글에 대해서만 부분적으로 갱신되며, 삭제 확정된 게시글은 이 기록에서 제외된다.
- **시리즈 목차 파일**: 같은 시리즈로 식별된 게시글 항목들을 모아놓은 실제 산출물(001의 `*_series.json`). 매 실행마다 배치 결정 전체와 비교해 재조정되며, 일치하지 않는 부분(누락, 더 이상 없는 소속, 제목 불일치)만 갱신되고, 배치 결정상 소속 게시글이 2개 미만이면 존재하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 이미 목차에 반영된 게시글의 제목이 바뀐 시점부터, 그 다음 정기 확인이 끝난 시점까지 목차의 제목이 실제 게시글 제목과 일치하게 된다(현재는 재확인 메커니즘이 없어 무기한 불일치가 지속된다).
- **SC-002**: 목차에 반영된 게시글이 삭제되거나 비공개로 전환된 시점부터, 그 다음 정기 확인이 끝난 시점까지 목차에서 해당 항목이 자동으로 사라지고, 그 사실이 커밋 메시지에서 확인 가능하다(현재는 감지·반영 메커니즘이 전혀 없어 죽은 링크가 무기한 남는다).
- **SC-003**: 공개 게시글 목록 조회 자체가 실패한 실행에서는 어떤 게시글도 삭제·비공개 전환으로 잘못 표시되지 않는다(목록 조회 실패와 개별 게시글 결측이 뒤섞이지 않는다).
- **SC-004**: 이 기능 도입으로 늘어나는 게시글별 조회 요청 수는 실제로 변경이 의심되는 게시글 수에 비례하며, 추적 중인 전체 게시글 수 전체를 매번 다시 조회하지 않는다.
- **SC-005**: 시리즈 구분 기준이 바뀐 게시글은, 그 다음 정기 확인이 끝난 시점까지 새로 식별된 시리즈의 목차에서 확인할 수 있게 된다(현재는 재분류 메커니즘이 없어 원래 시리즈에 무기한 남는다).
- **SC-006**: 배치 결정과 이미 일치하는 시리즈 목차 파일·항목은, 정기 확인이 반복되어도 다시 갱신되거나 커밋되지 않는다(실제로 달라진 부분만 변경된다).
- **SC-007**: 서로 다른 변경 내용을 만든 두 정기 실행의 커밋 메시지는 서로 다르며, 각 커밋 메시지만 보고도 그 실행에서 무엇이 생성·갱신·삭제됐는지 알 수 있다(현재는 매번 동일한 고정 문구만 사용된다).

## Assumptions

- 이 기능은 두 종류의 상태를 유지한다: (1) 001의 기존 처리 이력 데이터를 확장한 변경 감지용 기록(전체 제목·lastMod 포함), (2) 게시글의 현재 시리즈 소속을 저장하는 신규 배치 결정 기록. 배치 결정 기록의 구체적인 저장 형식은 이번 스펙이 아니라 이후 설계(`/speckit-plan`) 단계에서 정한다.
- 게시글이 실제로 수정되면 공개 게시글 목록 조회 시 얻는 해당 게시글의 수정 시각 값도 함께 갱신된다 — 저장소 관리자가 직접 확인한 사실이다.
- 공개 게시글 목록 조회가 성공하면 그 결과는 그 시점의 공개 게시글 목록으로서 정확하다고 간주한다(001이 이미 전제하고 있는 가정과 동일). 목록 조회 자체가 실패한 경우에만 이번 실행의 판단(제목 갱신·재분류·삭제 확정 모두)을 보류한다.
- 배치 결정과 실제 목차 파일 사이의 불일치를 해소하는 모든 조정(제목 갱신, 재분류로 인한 이동, 삭제·비공개 전환으로 인한 제거, 항목 부족으로 인한 파일 삭제)은 001과 마찬가지로 무검토 자동 push로 수행한다 — 문제가 발견되면 저장소 관리자가 직접(예: git revert) 되돌린다는 명시적 판단에 따른 것이다.
- 배치 결정 기록은 이번 실행에서 바뀐 게시글에 대해서만 부분적으로 갱신되지만, 실제 목차 파일과의 비교·반영(FR-008)은 매 실행마다 배치 결정 전체를 대상으로 이뤄진다.
- 재분류·신규 시리즈 생성 시 목차 파일의 생성 기준은 001의 기존 규칙(같은 시리즈에 속한 공개 게시글이 2개 이상)을 그대로 적용한다. 이 기준을 충족하지 못하는 동안은 게시글을 기존 파일에 남겨, 목차에서 완전히 사라지는 상태를 만들지 않는다.
- 커밋 메시지에 담을 Created, Updated, Deleted 요약을 만들려면, 반영 단계(FR-008~011)에서 실제로 무엇을 만들었는지·고쳤는지·지웠는지를 구조적으로 추적해야 한다. 이 추적 방식의 구체적인 형태(어떤 데이터 구조로 모을지, 커밋 메시지 문구 형식)는 이번 스펙이 아니라 `/speckit-plan` 단계에서 정한다.
- 이번 실행에서 반영할 변경이 전혀 없으면(선별된 재확인 후보도 없고 배치 결정과 실제 파일이 이미 일치하면) 커밋을 만들지 않는다 — 001의 기존 동작(`tistory-series-sync.yml`의 `git status --porcelain` 확인)과 동일하게 유지한다.
- 001의 정기 실행 주기나 커밋 방식 자체를 바꾸는 것은 이번 기능의 목표가 아니다 — 필요한 최소 변경만 가한다.
- 삭제된 게시글을 위한 새로운 사용자 대상 화면·페이지는 만들지 않는다.
- 이번 기능 도입 이전에 처리된 게시글처럼 "마지막으로 확인한 수정 시각" 기준값이 없는 기존 기록은, 값이 채워질 때까지 "변경 여부 불명"으로 간주해 다음 정기 확인에서 한 번은 확인 대상에 포함시킨다.
- 한 번에 확인 대상이 되는 게시글 수가 급격히 늘어나는 경우(예: 대량 재발행)에 대한 별도의 처리량 조절 전략은 이번 스펙에서 확정하지 않으며, 실제로 그런 상황이 관찰되면 그때 재검토한다.
