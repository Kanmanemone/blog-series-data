# Phase 0 Research: HTML 엔티티 디코딩 누락 수정 (&rarr;)

Technical Context에 미해결 NEEDS CLARIFICATION 항목은 없다. 이 문서는 구현 방식에 대해
실제로 판단이 필요했던 두 가지를 기록한다.

> **후속 갱신 (결정 3, 4 참고)**: 결정 1은 애초에 `&rarr;` 하나만 보고 내린 판단이었다.
> 구현·1차 converge 과정에서 같은 클래스의 두 번째 사례(`&times;`)가 실제로 또 나타나면서,
> "실측되는 대로 하나씩 등록"하는 방식 자체가 재발을 막지 못한다는 사용자 피드백을 받아
> 결정 3으로 설계를 보강했다("숫자 문자 참조는 표 없이도 결정적으로 풀 수 있다" +
> "모르는 이름은 조용히 통과시키지 않고 실패를 눈에 보이게 한다"). 이어서 사용자가
> "이름 있는 엔티티도 결국 표가 필요하다면, 화이트리스트를 손으로 유지할 이유가 뭐냐"고
> 다시 지적해, 결정 4에서 결정 1의 **"완전한 범용 엔티티 표는 과잉 설계"라는 판단 자체를
> 뒤집었다** — 다만 "수천 개짜리 최신 HTML5 표 전체"가 아니라 "1999년에 이미 고정된
> HTML 4.01/XHTML1 표(약 250개)"로 범위를 한정해, 완결성과 유지보수 부담 사이에서
> 절충했다.

## 1. &rarr;를 HTML_ENTITIES 맵에 어떻게 추가할 것인가

- **Decision**: `scripts/sync-tistory-series/index.js`의 기존 `HTML_ENTITIES` 객체에
  `"&rarr;": "→"` 한 줄을 추가하고, `decodeHtmlEntities`의 정규식
  (`/&amp;|&lt;|&gt;|&quot;|&#39;/g`)에 `&rarr;`를 대안(alternation)으로 포함시킨다.
- **Rationale**: 001의 기존 구조(정규식 + 룩업 객체)를 그대로 재사용하면 되는 문제다.
  이미 다섯 개 엔티티가 같은 패턴으로 들어가 있으므로, 여섯 번째 항목을 같은 방식으로
  추가하는 것이 기존 코드와 테스트 스타일에 가장 부합한다.
- **Alternatives considered**:
  - *범용 HTML 엔티티 디코딩 라이브러리(또는 완전한 명명 엔티티 테이블) 도입*: 기각.
    001 research.md §3이 이미 "혹시 모를 인코딩에 대비해 방어적으로 소수만 치환"하는
    정책을 명시적으로 채택했고, 이 저장소는 외부 npm 의존성이 0개인 것이 전제(package.json
    description)다. 실측된 엔티티가 여섯 개째일 뿐인 지금 시점에 일반화하는 것은
    범위를 벗어난 과잉 설계다.
  - *정규식을 `/&\w+;/`처럼 넓혀서 모든 명명 엔티티를 잡고 화이트리스트로만 걸러내기*: 기각.
    HTML_ENTITIES에 없는 키를 만나면 어떻게 처리할지(원문 유지 vs 제거)를 새로 정의해야
    하고, 이는 001이 의도적으로 피한 "알 수 없는 입력에 대한 임의 동작"을 다시 들여오는
    것이므로 기존 다섯-엔티티 방식과 일관되지 않는다.

## 2. 이미 저장된 잘못된 값을 어떻게 고칠 것인가 (재조회 vs 직접 수정)

- **Decision**: navigation_series.json과 .github/sync-state.json의 해당 title 값을
  `decodeHtmlEntities`로 실제로 얻게 될 값과 동일하게 직접 수정한다(라이브 사이트
  재조회 없음).
- **Rationale**: 게시글 원문 `<title>` 태그는 이미 로컬 확인(연구 단계에서 grep)으로
  "Navigation 2 &rarr; 3" 형태임이 알려져 있고, `&rarr;` → `→` 매핑은 표준 HTML5 명명
  문자 참조로 모호함이 없다. 네트워크 접근(라이브 사이트 재조회)을 이번 구현 범위에
  포함시키면 오프라인 환경에서 검증이 불가능해지고, 동기화 파이프라인의 정상 동작
  경로(재실행 시 자연 수렴)와 이번 일회성 보정을 혼동하게 된다.
- **Alternatives considered**:
  - *다음 정기 동기화 실행이 드리프트 감지로 알아서 고치게 두고 아무것도 안 함*: 기각.
    002의 드리프트 감지는 sitemap의 `lastmod`가 저장된 값보다 최신일 때만 재조회
    대상이 되므로(`isDriftCandidate`), 게시글 자체가 다시 수정되지 않는 한 이번 버그는
    스스로 고쳐지지 않는다 — 원인(디코더)을 고쳐도 과거에 이미 잘못 저장된 값은 남는다.
  - *동기화 스크립트를 한 번 강제 실행해서 고침*: 기각. 이 저장소에는 라이브 네트워크
    접근과 GitHub Actions 자격 증명이 필요하며, 이번 세션에서 재현·검증 가능한 방식이
    아니다. 값이 무엇이어야 하는지 이미 확실하므로 직접 수정이 더 간단하고 검증 가능하다.

## 3. "실측 후 하나씩 등록"이 재발을 막지 못하는 문제를 어떻게 구조적으로 해결할 것인가

`&rarr;`를 고치고 `.github/sync-state.json`을 감사하는 과정에서 `&times;`가 같은 방식으로
또 발견됐다(speckit-converge 1차 실행, T009-T011). 사용자가 이를 "주먹구구식"이라고
정확히 지적했다 — 세 번째 미등록 엔티티가 나타나면 정확히 같은 방식으로 또 조용히
깨질 것이기 때문이다. 이 결정은 결정 1을 대체하지 않고 보강한다.

- **Decision**: HTML 문자 참조를 두 종류로 나눠 다르게 취급한다.
  1. **숫자 문자 참조**(`&#39;` decimal, `&#x2192;` hex)는 `String.fromCodePoint`로
     범용 디코딩한다 — 특정 값을 미리 등록할 필요가 전혀 없다.
  2. **이름 있는 엔티티**(`&amp;`, `&rarr;`, `&times;` 등)는 여전히 화이트리스트
     (`NAMED_HTML_ENTITIES`)로만 처리하되, 디코딩 후에도 화이트리스트에 없는 이름 있는
     엔티티 패턴이 남아있으면 `extractTitle`이 예외를 던진다. 이 예외는 `run()`이 이미
     갖고 있던 `fetchPostTitle`/`fetchPostDetails` 호출부의 try/catch(001부터 존재 —
     "개별 게시글 조회가 실패해도 그 게시글만 건너뛰고 나머지는 계속 처리한다")에 그대로
     걸려, 그 게시글만 이번 실행에서 건너뛰어지고 명확한 에러가 로그에 남는다.
- **Rationale**: 숫자 문자 참조는 코드포인트가 곧 문자를 결정하므로 "모르는 값"이라는
  개념 자체가 없다 — 표를 만들 필요 없이 완전히 일반화해도 안전하다. 반면 이름 있는
  엔티티는 이름과 문자의 대응이 임의적이라(예: `&times;`가 "×"라는 사실은 표 없이는 알
  수 없음) 완전한 범용화가 결정 1에서 이미 기각한 "수천 개짜리 HTML5 엔티티 전체 표
  직접 구현"으로 이어진다. 대신 **화이트리스트 + 실패를 눈에 보이게 만들기**를 조합하면,
  새 이름 있는 엔티티가 나타나도 (a) 코드 규모를 키우지 않고 (b) 데이터가 조용히
  깨지는 대신 사람이 알아차릴 수 있는 형태로 실패한다. 이것이 "재발 방지"의 핵심이다 —
  재발하는 것은 특정 엔티티가 아니라 "모르는 입력을 조용히 통과시키는 코드 경로"였다.
- **Alternatives considered**:
  - *알려진 HTML5 named character reference 전체 표(약 2,000개)를 직접 내장*: 기각.
    외부 의존성 0개 정책은 지킬 수 있지만, 이 저장소가 실제로 마주치는 엔티티 종류(지금까지
    2개)에 비해 코드량이 지나치게 크고, 유지보수 부담(HTML 표준 개정 추적)만 새로 생긴다.
    화이트리스트 + 실패 감지 조합으로 "재발 방지"라는 실제 목표를 달성할 수 있으므로
    불필요하다.
  - *모르는 이름 있는 엔티티를 원문 그대로 두고 계속 진행(현재까지의 동작)*: 기각.
    이번 기능 전체의 발단이 된 바로 그 실패 모드다 — 사용자가 명시적으로 "재발 방지"를
    요구했으므로 유지할 수 없다.
  - *모르는 이름 있는 엔티티를 만나면 그 문자를 제거하고 계속 진행*: 기각. 제목이
    깨진 채로(엔티티가 사라진 채로) 조용히 저장되는 것은 "&times;가 그대로 노출되는 것"과
    본질적으로 같은 문제(추측된 값이 검증 없이 공개 데이터가 됨)이며, 오히려 원문이라도
    남는 현재 상태보다 못하다.
  - *새 재시도·큐 메커니즘을 도입해 건너뛴 게시글을 확실히 재처리*: 기각(범위 밖). 001/002가
    모든 fetch 실패에 대해 이미 "cutoff가 진행돼 일부 실패 후보가 다음 실행에 재시도되지
    않을 수 있다"는 특성을 갖고 있고(index.js의 관련 주석 참고), 이번 기능이 새로 만든
    문제가 아니다. 기존 실패 처리 경로에 올라타는 것으로 충분하며, 별도 재시도 장치를
    새로 설계하는 것은 이번 버그의 범위를 벗어나는 과잉 설계다.

## 4. 이름 있는 엔티티의 화이트리스트를 계속 손으로 유지해야 하는가

결정 3까지 반영한 뒤 사용자가 정확한 기술적 질문을 던졌다: "`String.fromCodePoint`로 다
해결되는 거 아니야?" 답은 "숫자 문자 참조는 그렇지만, 이름 있는 엔티티는 아니다"이다 —
`&rarr;`의 "rarr"라는 이름 자체에는 코드포인트 정보가 전혀 없고, 이름과 코드포인트의
대응은 HTML 표준이 정한 약속이라 표 없이는 절대 알 수 없다. 그렇다면 결정 3처럼 우리가
"실측된 것만" 표를 손으로 채우는 대신, 표준이 이미 확정해 놓은 표를 통째로 쓰면 되지
않느냐는 것이 사용자의 다음 질문이었다.

- **Decision**: `scripts/sync-tistory-series/htmlNamedEntities.js`에 HTML 4.01/XHTML1
  Recommendation(https://www.w3.org/TR/html4/sgml/entities.html)이 정의한 이름 있는
  문자 참조 표 전체(정확히 252개 — 기본 마크업 4개 + Latin-1 96개 + 기호·수학·그리스
  문자 약 122개 + 추가 특수 문자 약 30개)를 이름→코드포인트(숫자) 객체로 내장한다.
  `decodeHtmlEntities`는 이 표에서 코드포인트를 찾아 결정 3의 숫자 문자 참조와 동일하게
  `String.fromCodePoint`로 변환한다 — 이름 있는 엔티티와 숫자 문자 참조가 이제 하나의
  경로로 통합된다. `hasUnresolvedNamedEntity`/`extractTitle`의 실패 감지(결정 3)는
  그대로 유지해, 이 표에도 없는 진짜 예외(예: HTML5에서 새로 생긴 `&checkmark;`)에 대한
  최후 안전망 역할을 한다.
- **Rationale**: HTML 4.01은 1999년에 W3C Recommendation으로 확정된 뒤 이름 있는 문자
  참조 표가 바뀐 적이 없다 — "표준 개정을 계속 추적해야 하는 유지보수 부담"이라는 결정 1의
  기각 사유가 이 범위(HTML4까지)에는 사실상 적용되지 않는다. 252개는 손으로 입력해
  검증 가능한 크기이며(구현 단계에서 실제로 `String.fromCodePoint`로 spot-check함),
  정적 데이터 객체 하나를 추가하는 것뿐이라 외부 npm 의존성 0개 정책도 그대로 지킨다.
  이 표를 쓰면 지금까지 이 저장소가 겪은 두 사례(`&rarr;`, `&times;`)를 포함해 사람이
  실제로 타이핑할 만한 특수문자·기호·그리스 문자·화살표·수학 기호가 거의 전부 커버되므로,
  결정 3의 화이트리스트+실패감지 조합에서 "화이트리스트를 계속 손으로 넓혀야 하는" 절반을
  사실상 없앤다.
- **Alternatives considered**:
  - *결정 3의 6개짜리 손 관리 화이트리스트 유지*: 기각(사용자가 명시적으로 선택하지
    않음). 표준이 이미 답을 갖고 있는데 그걸 손으로 다시 만드는 것은 불필요한 반복
    작업이며, 세 번째 미등록 이름이 나타날 가능성을 결정 1보다는 줄였지만 여전히 남겨둔다.
  - *HTML5 Living Standard 전체 표(약 2,231개, MathML 전용 별칭 포함)를 내장*: 기각.
    HTML4 표보다 9배 가까이 크고, 그중 상당수(MathML 기호, 대소문자 별칭 등)는 이
    저장소의 한국어 기술 블로그 제목에 등장할 가능성이 사실상 없다. HTML5 표는 WHATWG가
    계속 개정하는 living standard라 결정 1이 우려한 "표준 개정 추적" 부담이 실제로
    존재하지만, HTML4 표는 고정돼 있어 그 부담이 없다 — 완결성과 유지보수 비용의
    절충점으로 HTML4 표를 택한다.
  - *외부 라이브러리(예: `he`, `html-entities`)로 표를 대체*: 기각. 이 저장소는
    외부 npm 의존성이 0개인 것이 전제(package.json description, 001 정책)이며, 표
    자체가 정적 데이터라 라이브러리를 추가할 이유가 없다.

## 5. 커밋 메시지의 8개 카테고리를 어떻게, 어디서 집계할 것인가

spec.md User Story 4가 요구하는 8개 카테고리 중 "시리즈" 5종(생성/항목 추가/항목 제거/
제목 갱신/삭제)은 이미 `reconcile()`이 파일 단위로 diff를 계산하고 있어 그 계산 결과를
재사용하면 되지만, "게시글" 3종(새 글/정보 갱신/삭제)은 `reconcile()`이 아예 건드리지
않는(시리즈에 속하지 않는) 게시글에 대한 것이라 다른 지점에서 잡아야 한다.

- **Decision**:
  1. `reconcile(assignments, rootDir)`의 반환값을 "파일별 CUD 항목 배열 + 사람이 읽는
     detail 문자열"에서 `{created, added, removed, retitled, deleted}` 5개 숫자 집계로
     바꾼다. 이 숫자는 기존에도 내부적으로 `diffItems`가 파일 단위로 계산하던 것을
     전체 실행에 걸쳐 합산한 것뿐이다 — 어떤 파일에서 발생했는지는 더 이상 반환하지
     않는다(User Story 4가 "파일명 나열 안 함"을 명시적으로 요구, FR-013).
  2. "게시글" 3종은 `run()` 자신이 각 게시글을 처리하는 바로 그 지점에서 직접 센다
     (reconcile()이 나중에 사후적으로 판별할 방법이 없으므로):
     - **새 글**: 001의 신규 후보 루프에서 (a) `seriesId === null`인 후보, 또는
       (b) `unmatchedBySeriesId` 그룹인데 형제(이번 실행 후보 + 과거 이력 중 지금도
       공개된 것)를 합쳐도 2명 미만이라 `createSeriesFile`이 파일을 만들지 않은 후보.
     - **정보 갱신**: 002의 드리프트 재확인 루프에서, 재조회 직전에 저장돼 있던
       "이전 제목"을 캡처해 새 제목과 비교한다 — (a) 그 게시글이 애초에 어떤 시리즈에도
       속하지 않았거나(`oldSeriesId`가 null), (b) 속해 있었지만 제목 텍스트가 실제로는
       바뀌지 않은 경우(재조회 사유가 lastMod/publishedAt 갱신뿐인 경우). 001 루프에서
       `appendToSeries`가 "이미 있는 URL"이라 false를 반환하는 드문 경우(같은 실행에서
       lastMod가 다시 바뀌어 후보로 재등장했지만 이미 시리즈 항목이었던 게시글)도 같은
       버킷으로 처리한다 — 이 경우도 sync-state.json만 갱신되고 시리즈 파일은 그대로다.
     - **삭제**: 002의 삭제 확정 루프에서, `markDeleted`된 게시글 중 `oldSeriesId`가
       null인 것(원래 어떤 시리즈에도 속하지 않았던 게시글).
     - **시리즈로 넘어가는 경우**(오래된 판정 로직 그대로 유지): `oldSeriesId`가 있고
       제목이 실제로 바뀌었으면 재분류든 단순 갱신이든 `updateAssignmentForPost`/
       `resolveReclassifyBatches`를 거쳐 `reconcile()`의 diff에 반영되므로, 그쪽에서
       세어진다(게시글 카운터에는 더하지 않음 — 이중 집계 방지).
  3. `buildCommitMessageBody(counts)`라는 새 순수 함수가 8개 숫자를 받아 "게시글"/
     "시리즈" 그룹으로 나눈 본문 텍스트를 만든다(0인 카테고리 줄 생략, 그룹 전체가
     0이면 헤더도 생략, FR-014·FR-015). N은 8개 숫자의 합이다(FR-016).
  4. `.sync-commit-summary.txt` 파일 형식을 바꾼다: 첫 줄에 N(정수)을, 이어지는 줄에
     본문을 쓴다. 워크플로우는 더 이상 `wc -l`로 줄 수를 세지 않고(그룹 헤더 줄까지
     세어버려 부정확해짐) `head -n1`로 N을 직접 읽는다.
  5. `buildNewPostCud`, `renderCommitSummary`, `CUD_TYPE_LABEL`은 더 이상 쓰이지 않으므로
     제거한다 — 파일별 상세를 포맷하던 코드였는데 새 형식은 카테고리 집계만 다루므로
     불필요해졌다(오버엔지니어링 방지 — 안 쓰는 코드를 남겨두지 않는다).
- **Rationale**: "시리즈" 카운트는 실제 파일 대 파일 diff가 있어야만 정확히 알 수 있는
  값이라(예: 제목이 텍스트상 정말 바뀌었는지) `reconcile()`이 가장 정확한 위치에서
  계산한다. "게시글" 카운트는 애초에 `reconcile()`이 보지 않는 영역(시리즈 미소속)의
  일이므로 `run()`이 직접 셀 수밖에 없다. 한 게시글이 같은 실행에서 001 루프와 002
  루프를 동시에 통과하는 일은 없다(002의 드리프트 판정은 001이 이미 갱신한 lastMod를
  기준으로 하므로, 001이 처리한 게시글은 같은 실행에서 002의 재확인 대상이 되지
  않는다) — 따라서 "게시글" 카운터와 "시리즈" 카운터 사이에 같은 게시글이 이중으로
  잡힐 가능성이 구조적으로 없다.
- **Alternatives considered**:
  - *`reconcile()`이 돌려주는 파일별 CUD 배열을 그대로 두고, 커밋 메시지 생성부에서
    사후적으로 재구성*: 기각. "게시글" 카테고리는애초에 `reconcile()`의 관찰 범위 밖이라
    사후 재구성이 불가능하고, 파일별 배열에서 "정말 텍스트가 바뀌었는지"를 다시
    계산하려면 diff 로직을 중복 구현해야 한다.
  - *게시글 단위로 개별 CUD 이벤트 배열을 만들고 나중에 카테고리별로 group-by*: 기각.
    최종 본문에 파일명·게시글 제목 같은 개별 상세를 아예 안 쓰기로 했으므로(User Story 4
    "최종 형식"), 배열을 만들었다가 group-by로 다시 숫자로 뭉치는 것은 불필요한 중간
    단계다 — 처음부터 숫자 카운터로 누적하는 게 더 단순하다.
