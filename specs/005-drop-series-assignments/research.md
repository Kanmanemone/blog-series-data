# Research: 배치 결정 파일 제거

## 결정 1. 배치 결정을 없애고 목차 파일만 기준으로 삼는다

- **Decision**: `.github/series-assignments.json`과 `seriesAssignments.js`, `reconcile.js`를 삭제한다. 동기화는 목차 파일을 읽어 메모리에서 고친 뒤 바뀐 파일만 쓴다.
- **Rationale**: 2026-10-10 기준 30개 그룹 전부 목차 파일과 구성·제목·순서가 같다(004 이후 검증). 배치 결정에만 있는 정보는 `publishedAt`인데, 처리 이력에도 같은 값이 있다. 복사본이 어긋나는 사고(004)와 수동 순서가 되돌아가는 문제(spec 배경)는 사본이 하나일 때만 사라진다.
- **Alternatives considered**:
  - 배치 결정을 유지하고 "목차 파일 순서를 배치 결정으로 역동기화" — 두 사본 동기화 로직이 하나 더 늘 뿐이고, 004 유형의 어긋남은 여전히 가능하다. 대화 중 사용자와 검토 후 기각.
  - 배치 결정에서 순서만 빼기 — 구성·제목 사본 문제는 남는다.

## 결정 2. 목차 편집 연산 네 가지

- **Decision**: `seriesFiles.js`에 `appendBatch(file, posts)`(이미 있는 URL은 건너뛰고, `orderByPublishedAt`으로 정렬해 끝에 붙임, 붙인 개수 반환), `retitleItem(file, url, title)`(바뀌었으면 true), `removeItem(file, url)`(뺐으면 true)을 둔다. 파일 삭제는 실행 마지막에 "이번에 손댄 파일 중 항목이 1개 이하인 것"만 지운다.
- **Rationale**: 002 재조정이 하던 일(추가·제거·제목 변경·2개 미만 삭제)을 그대로 덮으면서, 기존 항목 위치를 바꾸는 연산이 아예 없다 → FR-002가 구조적으로 보장된다.
- **Alternatives considered**: 기존 `diffItems`로 원하는 상태를 만들고 비교 — 원하는 상태를 다시 만들어야 해 결국 배치 결정과 같은 사본이 필요하다.

## 결정 3. "한 묶음"의 범위

- **Decision**: 같은 목차에 대해 (a) 001 단계에서 이번 실행에 새로 붙는 글 전체, (b) 001의 새 목차 생성 시 형제 전체, (c) 002 재분류 단계에서 같은 목표 시리즈로 옮겨가는 글 전체를 각각 한 묶음으로 본다. (a)와 (c)가 같은 목차에 겹치면 (a) 뒤에 (c)가 붙는다.
- **Rationale**: 두 단계는 순서대로 실행되고 (c)의 판단(목표 파일이 있는지)은 (a) 결과에 의존한다. 겹치려면 6시간 안에 같은 시리즈에 새 글과 재분류가 함께 일어나야 해 드물다. 단계를 합치면 `run()`의 구조를 크게 바꿔야 한다(오버엔지니어링).
- **Alternatives considered**: 실행 끝까지 붙일 글을 모았다가 한 번에 정렬 — 위 이유로 기각, spec Edge Cases에 명시.

## 결정 4. 공개 시각 정렬 규칙

- **Decision**: `orderByPublishedAt(posts)` — 안정 정렬, ISO 문자열 비교, `publishedAt`이 없는(null/undefined) 글은 뒤로. 새 목차 생성(`createSeriesFile`)도 이 함수를 쓰고 `listName`은 정렬 후 첫 글의 원시 시리즈명이다.
- **Rationale**: `publishedAt`은 모두 `Date#toISOString()` 결과(UTC, 같은 길이)라 문자열 비교가 시간 순과 같다. 과거 이력 형제의 공개 시각은 처리 이력 레코드에서 가져온다(`collectSiblingCandidates`가 함께 넘김) — 추가 요청 없음(SC-005).
- **Alternatives considered**: lastmod 유지 — 예전 글을 최근 수정하면 뒤로 가는 문제(spec 배경) 때문에 기각.

## 결정 5. 처리 이력 없는 목차 항목(수동 추가) 처리

- **Decision**: 001 단계에서 후보 URL이 이미 어떤 목차에 있으면(004의 `excludeAlreadyListed`를 통과했다면 = 처리 이력이 없거나 삭제 확정 레코드), 그 목차에서 제목만 그 자리에서 바꾸고 다른 목차에 붙이지 않는다. 제목이 같으면 "정보 갱신".
- **Rationale**: 지금은 이 경우 "정보 갱신"으로만 세고 제목이 안 바뀌며, 새 제목이 다른 기존 시리즈를 가리키면 그 목차에 또 붙어 중복이 생긴다. 이 실행 뒤에는 처리 이력이 생기므로 다음부터는 002가 재분류까지 맡는다.

## 결정 6. 커밋 요약 집계

- **Decision**: 손댄 파일마다 `{added, removed, retitled}`를 모으고, 실행 끝에 파일이 지워지면 "삭제" 1건만, 남으면 세 값을 그대로 더한다. 새로 만든 파일은 "생성" 1건만 센다. 이동은 옛 파일 제거 + 새 파일 추가.
- **Rationale**: 002 `reconcile()`의 집계(2개 미만 그룹 → 삭제 1건만, 새 파일 → 생성 1건만, 그 외 diff 건수)와 같은 의미를 유지한다(FR-008).

## 결정 7. 데이터 이전

- **Decision**: `git rm .github/series-assignments.json`, 워크플로우 두 개에서 해당 `git add` 분기 3줄 삭제. 목차 파일은 바꾸지 않는다.
- **Rationale**: 목차와 배치 결정이 이미 일치하므로 이전 작업이 필요 없다. 병합 전 main에서 봇이 배치 결정을 바꾸면(004 미병합 상태의 구 코드) 병합 시 수정/삭제 충돌이 나므로, 그때는 삭제 쪽을 택하면 된다(quickstart 참고).
