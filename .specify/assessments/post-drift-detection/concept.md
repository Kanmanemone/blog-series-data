# Concept: 게시글 드리프트(제목 변경·삭제) 감지 및 갱신

- **Slug**: post-drift-detection
- **Created**: 2026-08-08
- **Recommended option**: Option B — 제목 변경 자동 갱신 + 삭제 감지·플래그

## Options

### Option A — 삭제 감지만 (이미 계산되는 신호 재사용)
- **Sketch**: `seriesFiles.js`가 매 실행마다 이미 계산하고 버리는 sitemap 결측 신호(`collectSiblingCandidates`)를 재사용해, 시리즈 json에 반영된 게시글이 sitemap에서 사라졌는지만 감지하고 그 결과를 어딘가에 남긴다(예: 워크플로우 로그, 리포트 파일). 제목 변경 감지나 시리즈 json 자동 갱신은 하지 않는다.
- **Appetite**: small
- **Trade-offs**: 사실상 추가 요청 비용이 0에 가깝고(이미 계산 중인 값을 버리지 않고 쓰는 것뿐) 구현 위험도 가장 낮다. 다만 problem.md의 Goal 1(제목 변경이 결국 시리즈 json에 반영됨)을 전혀 만족시키지 못한다 — 감지만 하고 아무것도 갱신하지 않으므로 "정확성 유지"라는 목표에 절반만 답한다.
- **Rabbit holes**: 거의 없음 — 기존 계산 결과의 소비처만 바꾸는 수준이라 스코프가 새지 않는다.

### Option B — 제목 변경 자동 갱신 + 삭제 감지·플래그 (권장)
- **Sketch**: `processedPosts`에 게시글 처리 시점의 `lastmod`를 함께 기록해둔다. 매 실행마다 sitemap을 한 번 조회해 각 URL의 현재 `lastmod`를 `processedPosts`에 저장된 값과 비교하는 것만으로(추가 요청 없음) "이 게시글이 마지막 처리 이후 수정됐는가"를 저비용으로 판별한다. Tistory는 게시글 수정 시 sitemap의 `lastmod`를 실제로 갱신하므로, 이 값이 바뀐 게시글만 골라 그 소수에 대해서만 title을 재조회해 시리즈 json의 `title`을 자동 갱신한다(001과 동일한 "추가 성격" 안전 모델 — 값 갱신이지 항목 삭제가 아님). sitemap에서 아예 사라진 게시글은 같은 diff 과정에서 함께 드러나며(Option A와 동일한 URL 집합 비교), 시리즈 json에서 자동으로 제거하지는 않고 플래그·리포트로 남겨 관리자가 직접 판단하게 한다.
- **Appetite**: medium
- **Trade-offs**: problem.md의 두 Goal을 문서에 쓰인 그대로(제목 변경=자동 반영, 삭제=감지만) 정확히 만족시키고, 001이 채택한 "파괴적 조작은 하지 않는" 위험 등급을 그대로 유지한다. `lastmod` diff 덕분에 title 재조회 대상이 "실제로 바뀐 것으로 의심되는 소수"로 줄어들어, 331건 전체를 매번 재조회하던 방식보다 요청량 리스크가 크게 낮다. 대가로 `processedPosts`에 `lastmod` 필드를 추가로 저장·비교하는 로직과, "접근 실패 vs 실제 삭제" 구분 로직이 새로 필요하다.
- **Rabbit holes**: (1) `lastmod` diff로 걸러진 대상마저 많다면(예: 대량 재발행) title 재조회 요청이 순간적으로 몰릴 수 있음 — 그 경우의 대비책은 설계 단계 판단으로 남긴다. (2) 플래그를 "어디에" 남길지(이슈? 워크플로우 요약? 별도 리포트 파일?) 정하는 것 자체가 작은 UX 설계 문제로 번질 수 있다. (3) 접근 실패와 실제 삭제 구분 로직이 부실하면 오탐 플래그가 쌓여 신호로서의 가치가 떨어진다.

### Option C — 완전 자동 처리(삭제 시 자동 제거까지)
- **Sketch**: Option B와 동일하게 동작하되, 삭제·비공개 전환이 확인되면(예: 연속 N회 sitemap 결측) 시리즈 json 항목을 자동으로 제거하는 것까지 포함한다. intake.md에 원래 요청된 문구("게시글 제거 또는 제목 변경까지 감지하여 업데이트")를 문자 그대로 구현하는 안이다.
- **Appetite**: large
- **Trade-offs**: 사용자가 원래 표현한 요청을 가장 완전하게 구현하지만, research.md가 지적한 위험 등급 불일치를 그대로 안고 간다 — 001은 "추가만 하는" 무검토 자동 push 모델을 전제로 안전하다고 판단했는데, 여기서는 같은 무검토 자동 push 모델 위에 "항목 제거"라는 파괴적 조작을 얹게 된다. 일시적 오류(네트워크 오류, 일시적 5xx)를 삭제로 오판하면 살아있는 항목이 조용히 사라질 수 있어, 이를 막을 신뢰할 수 있는 확정 로직(연속 재확인 횟수, 백오프·재시도 등)이 선행되어야 안전하다.
- **Rabbit holes**: 오탐 방지 로직(연속 확인 횟수, 재시도/백오프) 자체가 하나의 작은 설계 프로젝트가 될 수 있고, 완성도가 낮으면 "블로그에서 멀쩡한 시리즈 항목이 사라지는" 형태로 사고가 날 수 있다. 이 안전장치를 제대로 만들기 전에는 착수하지 않는 편이 낫다.

## Recommendation

**Option B**를 권장한다. problem.md의 Goal 1("제목 변경이 수동 개입 없이도 결국 반영된다")은 실제 갱신 동작을 요구하므로 Option A로는 충족되지 않는다. 반면 Goal 2는 "최소한 감지되어 관리자가 인지"까지만 요구하고, Non-Goals가 "즉시 자동 삭제 여부는 이 문서에서 확정하지 않는다"고 명시적으로 유보했으므로, 삭제는 감지·플래그로 충분하며 Option C의 자동 삭제까지 갈 필요가 없다. Option B는 기존에 이미 존재하는 두 패턴(`seriesFiles.js`의 sitemap 결측 계산, `index.js`의 processedPosts 제목 재조회)을 그대로 재사용해 Goal 3(새 데이터 구조를 만들지 않고 기존 기반 위에서 동작)도 만족시킨다. 무엇보다, 001이 신중하게 선택한 "파괴적 조작 없는 무검토 자동 push" 위험 등급을 그대로 유지한다는 점에서 research.md가 지적한 위험 등급 불일치를 이번 기능 범위에서 피해간다.

Option C는 배제하지 않되, 지금 착수하기에는 이르다고 본다 — 오탐 방지를 위한 확정 로직이 설계되지 않은 채 파괴적 자동화를 얹는 것은 problem.md의 Non-Goals가 이미 유보한 판단을 앞서가는 것이다. Option B가 쌓아 둔 플래그 데이터를 관찰한 뒤, 필요하다면 별도 후속 아이디어로 Option C를 다시 상정하는 편이 안전하다.

## Out of Scope (for Option B)

- 삭제·비공개 전환 게시글의 시리즈 json 자동 제거(Option C 영역 — problem.md Non-Goals가 이미 유보)
- seriesId 자체가 바뀌는 재분류 처리(intake.md NEEDS CLARIFICATION, problem.md Non-Goals)
- 001 워크플로우의 예약 주기·커밋 방식 자체를 바꾸는 것(재확인 스텝 추가에 필요한 최소 변경 외에는 다루지 않음)
- 삭제된 게시글에 대한 신규 사용자 대상 기능(예: 안내 페이지)
- title 재조회 대상이 예상보다 많아지는 경우(대량 재발행 등)에 대한 배치/스로틀링 전략의 구체적 형태 — `lastmod` diff로 대상을 좁힌 뒤에도 남는 우발적 리스크이며, 설계 단계(`/speckit-specify` 이후)의 판단으로 남긴다

## Assumptions to Validate

- ~~Tistory가 게시글 수정 시 sitemap의 `lastmod`를 실제로 갱신하는지~~ — **확인됨**: 저장소 관리자가 직접 확인한 사실이다. `lastmod` diff를 title 재조회 대상 축소의 근거로 그대로 사용할 수 있다.
- `processedPosts`에 `lastmod`를 추가로 저장하는 것이 `.specify/memory/constitution.md` Principle I(시리즈 json 스키마 고정)에 저촉되지 않는다 — research.md가 이미 확인했듯 이런 부기 정보는 `*_series.json`이 아니라 `sync-state.json` 쪽에 두는 것이 맞으므로 저촉 가능성은 낮지만, 스펙 단계에서 명시적으로 확인한다.
- 삭제 플래그를 관리자가 실제로 인지할 수 있는 노출 지점(예: GitHub 이슈, 워크플로우 실행 요약, 별도 리포트 파일)이 이 저장소의 기존 운영 방식과 잘 맞는다 — 스펙 단계에서 구체적 메커니즘을 정해야 한다.
- 001 배포(2026-07-21/22) 이후 실제로 드리프트가 발생한 사례가 있는지는 아직 확인되지 않았다(research.md) — 스펙 착수 전에 수동 sitemap diff로 한 번 검증해 두면 긴급도 판단에 도움이 된다.
- `seriesFiles.js`의 `collectSiblingCandidates`가 계산하는 sitemap 결측 신호를 기존 용도(형제 게시글 수 임계값 판단)를 깨지 않고 재사용하거나 리팩토링할 수 있다 — 스펙·플랜 단계에서 코드 수준으로 확인이 필요하다.
